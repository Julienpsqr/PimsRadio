# 002 — Validation du compose et du script Liquidsoap

**Statut** : spécifié · **Priorité** : P0 · **Dépend de** : rien · **Bloque** : 001, 003, 004

> **EN summary.** Prove, with a fully automated and repeatable script (`npm run test:engine`), that the generated Liquidsoap script is valid for a pinned Liquidsoap version, that Icecast receives and serves the stream, that the fallback folder plays when the queue is empty, that a file pushed over telnet into `request.queue` is played, that priority live > queue > fallback holds, and that the output never goes silent while at least one fallback track exists. Test audio is synthesised (sine tones at distinct frequencies, generated by Liquidsoap itself in a container, no download, no ffmpeg on the host). Everything runs on non-default localhost ports with throw-away passwords and is torn down at the end. Out of scope: TypeScript telnet client (item 001) and any UI.

## Questions ouvertes

Aucune ne bloque. Voir la section finale (versions d'images à vérifier par l'implémenteur : l'agent Spécification n'a pas pu interroger le registre Docker).

## 1. Contexte et problème

Le script `src/engine/liquidsoap.ts` et `deploy/docker-compose.dev.yml` n'ont jamais été exécutés. Le comportement réel de Liquidsoap (noms des commandes telnet, comportement de `fallback`, de `mksafe`, de `request.queue` à vide, reconnexion Icecast) conditionne le client telnet (001), la détection de silence (003) et l'aircheck (004). Qui : le mainteneur/développeur, avant d'écrire du code qui s'appuie sur le moteur ; plus tard la CI et chaque changement du générateur. Quand : avant tout autre élément P0. Une erreur de syntaxe ou de logique ici = radio muette en production (ADR 0001).

Points du brouillon à vérifier explicitement (hypothèses, pas des faits) :
- la version `savonet/liquidsoap:v2.3.0` et l'image `libretime/icecast:2.4.4` existent-elles, en arm64 ET amd64 ? ;
- `normalize(radio)` existe-t-il et fait-il ce qu'on veut en 2.x (sinon remplacer par une fonction valide ou retirer ; décision dans le générateur) ;
- `playlist(... reload_mode="watch")` sur un dossier vide ou monté en volume Docker macOS ;
- le préfixe des commandes telnet (`auto.push`, `auto.queue`, `auto.skip`) avec `request.queue(id="auto")` ;
- le compose publie le port 8005 (harbor) mais pas le telnet 1234 ; Icecast écoute sur 8000 dans le conteneur ;
- les mots de passe par défaut `change-me` dans le compose/gen-engine ne doivent pas servir pour le test.

## 2. Comportement attendu

### Parcours du script `npm run test:engine` (cas nominal)

1. **Pré-vol** : Docker joignable (`docker info`), sinon sortie code 2 avec message clair « Docker indisponible » (distinct d'un échec de test, code 1).
2. **Épinglage** : les images sont lues depuis un seul endroit (le compose), par tag précis (jamais `latest`). L'implémenteur vérifie avec `docker manifest inspect` que chaque tag existe pour `linux/arm64` et `linux/amd64`, choisit la dernière 2.x stable existante (tag `vX.Y.Z`), et consigne dans le compose un commentaire avec la date de vérification. Idéal : ajouter aussi le digest.
3. **Sons de test** : générés dans un dossier temporaire (`os.tmpdir()`/dossier de run, jamais commité), par un conteneur Liquidsoap jetable (`docker run --rm`) qui écrit des MP3 depuis un oscillateur (`sine`) : 
   - secours : 2 fichiers de 20 s à 440 Hz ; 
   - file : 1 fichier de 8 s à 880 Hz ; 
   - direct : flux émis à 1320 Hz (voir plus bas) ; 
   - fichier corrompu : quelques octets aléatoires nommés `.mp3`.
   Les fréquences distinctes permettent d'identifier *quelle source* joue, sans dépendre du contenu.
4. **Génération du script** par `generateScript` (même code que `npm run gen-engine`), avec ports de test et mots de passe de test, écrit dans le dossier temporaire du run (pas dans `engine/generated/`).
5. **Démarrage** du compose de test (`docker compose -p pimsradio-test ...`), avec le compose dev paramétré par variables d'environnement (ports, mots de passe, chemins) afin de ne pas dupliquer le fichier ; un fichier d'override `deploy/docker-compose.test.yml` est autorisé.
6. **Attente de disponibilité** : sonder `http://127.0.0.1:18000/status-json.xsl` jusqu'à ce que le mount `/radio` apparaisse (délai max 60 s, sinon échec avec les logs du conteneur).
7. **Mesures** (voir critères), puis **arrêt et nettoyage** (toujours, même en cas d'échec, d'interruption Ctrl-C ou d'exception : `docker compose down -v --remove-orphans`, suppression du dossier temporaire). En cas d'échec, les logs Liquidsoap/Icecast sont affichés (mots de passe masqués) avant le nettoyage.
8. Sortie : un résumé lisible « critère → OK/KO » et le code de sortie 0 (tout OK), 1 (au moins un KO), 2 (environnement : Docker absent, port occupé).

### Méthode de mesure audio

- Capture du flux : lecture HTTP de `http://127.0.0.1:18000/radio` pendant N secondes (par Node, sans dépendance), écriture en MP3 temporaire.
- Décodage : par un conteneur Liquidsoap jetable (décodage MP3 vers WAV mono 8 ou 16 kHz) car ffmpeg n'est pas installé sur l'hôte.
- Analyse : petit module TypeScript sans dépendance qui lit le WAV, calcule le niveau RMS en dBFS par fenêtre de 500 ms et l'énergie à 440 / 880 / 1320 Hz (algorithme de Goertzel). Une fenêtre est « silencieuse » si RMS < −50 dBFS. Une fréquence est « dominante » si son énergie est ≥ 10× celle des deux autres. Ce module a ses propres tests unitaires (`node:test`, signaux synthétiques, sans Docker) dans `npm test`.
- Le MP3 introduit une latence et un tampon : ignorer les 3 premières secondes de chaque capture et tolérer une transition de ≤ 5 s autour d'un changement de source.

### Cas d'erreur du script lui-même
- Port de test déjà occupé : code 2, message nommant le port.
- Timeout d'un critère : KO avec la valeur mesurée, jamais de blocage infini (timeout global du script : 5 min, puis nettoyage forcé).
- Reste d'un run précédent (projet `pimsradio-test` existant) : nettoyé au démarrage.

## 3. Critères d'acceptation

Dans chaque cas « mesure » : Given = la pile de test démarrée comme ci-dessus.

1. **Script valide.** Given le script produit par `generateScript` avec la config de test, When on exécute la validation syntaxique de Liquidsoap (`liquidsoap --check` ou équivalent de la version épinglée) dans un conteneur, Then code 0 et aucune erreur/avertissement de type « fonction inconnue » ; une altération volontaire du script (ligne invalide) fait échouer la même vérification (test du test).
2. **Versions épinglées.** Given le compose, Then aucune image n'utilise `latest` ou un tag flottant, et chaque tag est référencé une seule fois ; un test unitaire (sans Docker) lit le compose et vérifie cela.
3. **Icecast reçoit et diffuse.** Given la pile démarrée, When on interroge `status-json.xsl`, Then le mount `/radio` existe, a une source, `listenurl`/`server_type` audio/mpeg, et un client HTTP sur `/radio` reçoit un flux MP3 (en-tête `Content-Type: audio/mpeg`, ≥ 16 ko en 5 s).
4. **Secours si file vide.** Given aucun fichier poussé dans la file et 2 fichiers à 440 Hz dans le dossier de secours, When on capture 10 s, Then la fréquence dominante est 440 Hz et aucune fenêtre n'est silencieuse (après les 3 s d'amorçage).
5. **Push telnet.** Given la file vide, When on se connecte en TCP brut au port telnet de test (127.0.0.1:11234) et qu'on envoie la commande de push du fichier à 880 Hz (chemin visible dans le conteneur), Then la réponse contient un identifiant de requête (RID) numérique, la commande de lecture de la file liste ce RID, et dans les 15 s la capture est dominée par 880 Hz. Le test envoie `exit` et ferme proprement la connexion.
6. **Retour au secours.** Given le fichier de la file terminé, When on capture 10 s de plus, Then la fréquence dominante redevient 440 Hz sans fenêtre silencieuse (pas de trou supérieur à 2 s lors de la transition).
7. **Priorité direct > file > secours.** Given la file contient un fichier long (≥ 60 s à 880 Hz) en cours de lecture, When un flux direct à 1320 Hz se connecte au harbor (mount `live`, mot de passe de test, conteneur jetable émettant vers le réseau du compose), Then dans les 10 s 1320 Hz domine ; When le direct se déconnecte, Then 880 Hz redomine (la file reprend) ; When la file est vidée (skip), Then 440 Hz redomine. À chaque transition, aucune fenêtre silencieuse > 2 s.
8. **Mot de passe harbor.** Given un émetteur avec un mauvais mot de passe, When il tente de se connecter au harbor, Then il est rejeté et la sortie reste inchangée.
9. **Fichier invalide poussé.** Given un fichier corrompu ou inexistant poussé dans la file, Then la commande répond sans faire tomber Liquidsoap, le flux ne devient pas silencieux > 2 s (le secours prend le relais) et le conteneur Liquidsoap reste `running`.
10. **Jamais silencieux.** Given l'enchaînement de 4 à 9 sur une capture continue (ou plusieurs captures bout à bout) d'au moins 90 s, Then aucune fenêtre ne dépasse 2 s consécutives sous −50 dBFS hors période d'amorçage.
11. **Reconnexion Icecast.** Given la pile en marche, When on arrête puis redémarre le conteneur Icecast, Then dans les 30 s le mount `/radio` réapparaît dans `status-json.xsl` et un client reçoit de nouveau de l'audio non silencieux, sans redémarrer Liquidsoap. Si la version épinglée ne le permet pas avec le script actuel, le générateur est corrigé (option de reconnexion de `output.icecast`) dans cet élément.
12. **Redémarrage du moteur.** Given Liquidsoap redémarré (`docker compose restart liquidsoap`), Then le flux revient en ≤ 30 s, joué depuis le secours.
13. **Secours vide (limite documentée).** Given le dossier de secours vide et la file vide, Then le flux Icecast reste connecté (la source reste listée, des octets arrivent) ; le silence est alors attendu et c'est consigné comme tel (le test vérifie la continuité du flux, pas l'audio). Ce comportement est écrit dans la doc d'exploitation.
14. **Nettoyage.** Given la fin du script (succès, échec, Ctrl-C), Then `docker ps -a` ne liste aucun conteneur du projet `pimsradio-test`, aucun réseau ni volume restant, aucun processus Node enfant, dossier temporaire supprimé.
15. **Isolation.** Given le script, Then tous les ports sont liés à `127.0.0.1` (jamais `0.0.0.0`), n'entrent pas en conflit avec 8000/8005/1234 du compose dev, et aucun mot de passe de test n'apparaît dans la sortie ni dans les logs conservés.
16. **Analyseur audio.** Given des signaux synthétiques (silence, 440 Hz, mélange), When le module d'analyse les traite, Then il détecte silence/dominante correctement (tests sans Docker, dans `npm test`).
17. **Commande et CI.** Given `npm run test:engine`, Then il est distinct de `npm test` (qui ne lance pas Docker et reste rapide). Un job CI optionnel (manuel ou nocturne, runner avec Docker) peut l'exécuter ; son absence ne bloque pas la CI principale.

## 4. Cas limites

- **Moteur en panne** : couvert par 11, 12, 13. Un Liquidsoap qui ne démarre pas (script invalide) doit être détecté au pré-vol (critère 1) et par le délai d'attente de l'étape 6.
- **Base vide** : sans objet (aucune base) ; l'équivalent est le dossier de secours vide (13).
- **Fuseau / heure d'été** : sans objet pour ce test ; aucune horloge murale n'est utilisée dans les assertions (durées relatives uniquement, pas de test dépendant de l'heure locale). Conteneurs en UTC.
- **Entrée invalide** : fichier corrompu/inexistant (9), mauvais mot de passe harbor (8), chemin avec espaces ou guillemets : le générateur doit échapper (déjà `lqString`) ; ajouter un test de génération avec un chemin contenant `"` et `\` validé par `--check` (1).
- **Flux qui tombe** : direct qui se coupe (7), Icecast qui tombe (11).
- **Concurrence** : deux connexions telnet simultanées poussant chacune un fichier ; les deux RID sont distincts et les deux fichiers sont joués dans l'ordre (client telnet réel : 001). Un seul run de `test:engine` à la fois : verrou (fichier ou nom de projet Docker) ; un second lancement échoue avec le code 2.
- **Arm64 / amd64** : le test tourne sur arm64 (OrbStack) ; l'existence des tags amd64 est vérifiée car la production sera probablement amd64.
- **Docker macOS** : les volumes sont montés depuis le dossier temporaire de l'utilisateur (visible par OrbStack) ; ne pas utiliser `/tmp` ni le répertoire de scratchpad hors des chemins partagés si le montage échoue.
- **Lenteur de la machine** : tolérances en secondes ci-dessus ; un échec ne doit venir que d'un dépassement net, pas d'une variation de 1 s. Pas de test flaky : si une assertion est instable, élargir la fenêtre plutôt que réessayer silencieusement.

## 5. Impact fiabilité

Cet élément n'ajoute aucune fonction en production : il ne tourne ni dans le plan de contrôle ni à l'antenne. Il réduit le risque de silence en prouvant que le moteur seul (Icecast + Liquidsoap + dossier de secours) joue sans PimsRadio (ADR 0001). Critère 12/13 : une panne du plan de contrôle équivaut à « file vide », donc le secours joue. Les corrections apportées au générateur (reconnexion, `normalize`, etc.) doivent être jugées sur ce critère.

## 6. Sécurité, vie privée, MCP

- Mots de passe de test : générés aléatoirement à chaque run (préfixe `test-`), transmis au compose par variables d'environnement du processus, jamais écrits dans le dépôt, jamais journalisés (masqués), jamais réutilisés pour le dev ni la production. Les valeurs `change-me` du compose dev restent des placeholders explicites de développement et ne sont jamais acceptées par un futur installateur.
- Ports liés à 127.0.0.1 ; le telnet Liquidsoap n'est jamais publié hors localhost (il n'a pas d'authentification) ; en dev le compose ne publie que ce qui sert. Le script ne doit pas modifier la publication du port telnet du compose dev sans l'indiquer (à corriger : en dev, le publier sur 127.0.0.1 uniquement).
- Aucun téléchargement de contenu audio (droits) ; aucune donnée personnelle ; aucune requête réseau externe hors tirage des images Docker.
- Images : tags épinglés, provenance officielle (Savonet pour Liquidsoap) ; justifier le choix de l'image Icecast (mainteneur, mise à jour) dans le commit.
- **Droits MCP** : pas de fonction de produit nouvelle, donc pas d'outil MCP à créer pour cet élément. Précision demandée : l'outil MCP « état du moteur » (niveau **lecture**) relève de 001/003 ; ici, aucune action d'antenne n'est exposée. Le test n'est pas invocable via MCP.
